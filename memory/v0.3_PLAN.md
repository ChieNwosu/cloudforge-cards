# CloudForge Cards v0.3 - Perpetual Learning Mode (Planning Only)

Status: PLAN ONLY. No implementation. Main 3-round game and v0.2.5 scoring engine stay untouched.
Copy: US English, no em dashes.

---

## 1. Product Recommendation

Add one new top-level destination: "Perpetual Learning" (a learning hub) that sits beside the
existing "Play" game. The current game stays exactly as is and becomes the "Ranked / Challenge"
experience. Perpetual Learning is the low-pressure study side.

Recommended information architecture:
- Top nav: Play | Learn | Leaderboard | How to Play   (Learn = Perpetual Learning hub)
- Inside Learn hub, a mode picker: Learn (flashcards), Test (quiz), Match (pipelines).

Certification Prep: recommend it be a FILTER LAYER across Learn, Test, and Match, not a 4th mode.
Reasons:
- The same flashcards, questions, and pipelines are reused; only the tag filter changes.
- A separate 4th mode would duplicate UI and fragment content authoring.
- Learners think "I want to study for SAA," then choose how (read, quiz, build), which maps to a
  cert selector at the hub level that scopes all three modes.
Implementation: a persistent "Exam track" selector at the top of the Learn hub with values
All, CLF/SAA, AIF, MLA, Mixed. It writes one piece of state (activeTrack) consumed by every mode.
A small "Certification Prep" entry card on the hub can deep-link into the track-scoped views so it
still feels like a first-class feature without being a separate engine.

Fit with existing game: shared content (service cards), shared visual identity, shared Professor
Flock. The game scoring engine is not touched. Learn modes have their own lightweight scoring.

## 2. v0.3 Scope Definition

Must-have (v0.3 core):
- Perpetual Learning hub + route, mode picker, exam-track selector (filter layer).
- Learn mode (flashcards) over existing service cards.
- Test mode (15 questions, MCQ + true/false + scenario select), score, review, explanations.

Nice-to-have (defer to v0.4+):
- Drag-and-drop for Match (tap-select ships first).

Explicitly deferred to v1 / later:

- DynamoDB, Bedrock AI feedback, AWS-native migration.

## 3. UX / UI Plan

Routes (React Router, additive, no changes to existing routes):
- /learn                      Perpetual Learning hub (mode picker + exam-track selector)
- /learn/cards                Learn mode (flashcards)
- /learn/test                 Test mode (quiz flow)
- /learn/match                Match mode (pipeline builder)
- Certification Prep is not its own route; it is the activeTrack filter shown on /learn and carried
  into the three sub-routes via query param (for example /learn/test?track=saa) or shared state.

Entry points:
- Top nav "Learn" link.
- A card on the Landing page hero/section ("Study anytime with Perpetual Learning").
- After a game's final summary, a soft prompt: "Sharpen up in Learn mode" linking to /learn.

Page layouts:
- Hub (/learn): Professor Flock bust greeting at top, exam-track selector (segmented control),
  three large mode cards (Learn, Test, Match) each with a one-line description and progress hint.
- Learn (/learn/cards): search bar + category filter (reuse Play filter row pattern with the new
  swipe affordance), grid of flippable cards. Card front = service name + category + icon; back =
  description, tags, core use cases, common pairings, anti-patterns, and a Flock study note.
  Per-card "Known / Review later" toggle. No timer, no score.
- Test (/learn/test): one question per screen, progress meter (Question X of 15 + bar), answer
  options, Submit, then inline correct/incorrect with explanation and an optional Flock note.
  End screen: count-up score, confetti on strong performance, full review list.
- Match (/learn/match): a prompt + an empty pipeline with labeled slots and a tray of candidate
  services. Tap a service then tap a slot (or drag later). Submit gives partial credit, marks each
  slot correct/misplaced/missing, and Flock explains gaps.

Professor Flock in UI (using Concept D):
- Hub: bust portrait as the onboarding greeter.
- Mode headers: small circular avatar (mentor avatar).
- Hint bubbles: portrait-in-speech-bubble (matches the "Great choice!" callout in the concept).
- Test review and result screen: result coach pose (Excited expression for high scores, Helpful
  for mixed, Thinking for low).
- Expressions to use later: Excited, Thinking, Helpful (already in the concept sheet).

Mobile behavior:
- Single column everywhere. Reuse the v0.2.6 patterns: min-w-0 on flex children, break-words on
  text, cf-hscroll for any horizontal row, no full-page horizontal scroll at 390px.
- Flashcard flip uses CSS transform; large tap targets; avatar shrinks to 32 to 40 px on mobile.

Audio controls (when added later):
- A single persistent mute/unmute toggle in the nav or hub header, state in localStorage
  (cf_audio_muted). Default muted to respect autoplay policies. No audio without user gesture.

## 4. Data Model Plan (content as static JSON first, API later)

Service cards (extend existing seed, additive fields only, no rewrite):
- existing: id, title, category, description, tooltip, difficulty, tags, cost, security,
  scalability, complexity, serverless
- ADD now (safe, optional): use_cases[], common_pairings[] (service ids), anti_patterns[],
  exam_tracks[] (for example ["clf","saa"]), domains[] (exam domain labels)

Flashcards: derived from service cards (no separate store needed). Optional study_note field per
card for the Flock note. Local progress kept client-side: { cardId: "known" | "review" }.

Question bank (new JSON, e.g. backend/content/questions.json):
- id, type ("mcq" | "truefalse" | "scenario_select"), prompt, options[], answer (index or set),
  explanation, exam_tracks[], domains[], difficulty, related_service_ids[]

Pipeline / match exercises (new JSON, e.g. backend/content/pipelines.json):
- id, title, prompt, slots[] (ordered expected service ids), distractors[] (service ids),
  allow_partial (bool), explanation, exam_tracks[], domains[]

Certification metadata (new JSON, e.g. backend/content/tracks.json):
- track id ("clf","saa","aif","mla"), display name, domains[] (objective labels), description

Progress tracking (v0.3 = local only):
- localStorage keys: cf_learn_progress (known/review map), cf_test_last (score, date),
  cf_completion (per-mode/track completion marks), cf_audio_muted, cf_player_name (existing).
- Fields chosen so a later server/DynamoDB sync can adopt the same shapes without a rewrite.

Fields safe to add now without forcing a rewrite: exam_tracks[], domains[], use_cases[],
common_pairings[], anti_patterns[] on service cards. They are ignored by the current game.

## 6. Backend / API Plan

Principle: content is mostly static and can ship as JSON read by the frontend or served read-only.
Add API only where grading should not be trivially visible to the client.

Optional new endpoints (read-only content):
- GET /api/learn/cards            (or reuse GET /api/cards/services + new fields)
- GET /api/learn/questions?track= (returns questions WITHOUT the answer key if graded server-side)
- GET /api/learn/pipelines?track=
- GET /api/learn/tracks

Optional grading endpoints (keep answers off the client):
- POST /api/learn/test/grade      { answers[] } -> { score, perQuestion[] explanations }
- POST /api/learn/match/grade     { placements } -> { partial_score, per_slot[], explanation }

Required vs optional:
- Required for v0.3: none strictly. Learn and a basic Test can run fully client-side from static
  JSON for speed of delivery.
- Recommended: server-side grading for Test and Match so answer keys are not shipped to the
  browser. This is the main reason to add backend endpoints. Decide per budget.
Local/static vs API: flashcard content can stay static. Question/pipeline answer keys should be
API-graded if we care about integrity; otherwise static is fine for an MVP.

## 7. Content Strategy

Authoring:
- Keep content in versioned JSON files under backend/content/ (questions.json, pipelines.json,
  tracks.json) and extend seed_data.py service cards with the additive fields.
- One question = one object with exam_tracks[] and domains[]. Authors add a question once and tag
  it for every exam it serves, so CLF/SAA/AIF/MLA share a single pool filtered by tag.
Structure CLF/SAA vs AIF vs MLA cleanly:
- Do NOT fork the content per exam. Use exam_tracks[] tags on shared items. A question can be
  ["clf","saa"]. AIF/MLA items get ["aif"] / ["mla"]. The track selector filters the pool.
Tagging system: exam_tracks[] (cert), domains[] (exam objective), difficulty, category, and
related_service_ids[] for cross-linking flashcards to questions.
Scalable expansion: new content = append JSON objects with tags. No schema change, no code change.
Add a small content-count sanity test so a malformed item fails fast.

## 8. Gamification Plan (practical, not bloated)

- Count-up score: simple requestAnimationFrame or a tiny interval on the Test result number.
- Confetti: a lightweight canvas confetti (small dependency) fired only on strong performance
  (for example >= 80 percent). Guard behind reduced-motion preference.
- Completion indicators: per-mode/track checkmarks and a "cards reviewed" count from local progress.
- Study streaks: optional, local only (cf_streak with last-active date). Keep it quiet, no pressure.
- Sound effects: defer to a later phase (see audio). Wire a single mute toggle first so audio can
  drop in cleanly.
Keep all of this opt-in and respectful of prefers-reduced-motion.

## 11. Risks and Rollback

Biggest risks:
- Content sprawl and inconsistent tags (mitigate with one tagged pool + a content sanity test).
- Match-mode interaction complexity on mobile (mitigate: tap-select MVP before drag-and-drop).
- Bundle bloat from images/confetti/audio (mitigate: WebP/AVIF, lazy-load, small libs, code-split
  the /learn routes so the game bundle is unaffected).
- Scope creep into accounts/AI (explicitly deferred).
Avoid bloat: reuse existing components, keep content static-first, code-split Learn routes.
Rollback: because Learn is additive and route-isolated, a failing phase can be hidden by removing
its nav link / route without touching Play, scoring, or leaderboard. Each phase is its own commit.

---

## 12. Final Recommendation (build order)

1. Phase 0 then Phase 1 (Learn flashcards) for highest ROI and lowest risk. It reuses existing
   cards, ships the Flock character upgrade, and gives immediate study value.
2. Phase 2 (Test) next; add server-side grading if integrity matters.
3. Phase 4 (Certification filter) layered on as soon as Learn + Test exist, since it is just tag
   filtering over what already works.
4. Phase 3 (Match) after, starting with tap-select.
5. Phase 5 (audio/polish) last.
Start with Learn mode. It is the safest, most reusable, and most visibly valuable first step.

## Future Architecture (governance-first, zero-trust-inspired, AWS migration-aware)

Auth (plan only, not in v0.3):
- Preferred future provider: Microsoft identity platform (Entra) via OpenID Connect / OAuth 2.0.
  Good fit for campus, enterprise, and student identity. No password storage in CloudForge.
- AWS-native alternative: Amazon Cognito user pools. Better when the app is fully AWS-owned and you
  want managed pools close to other AWS services.
- Tradeoff: Entra wins for institutional/student SSO and governance; Cognito wins for AWS-native
  ownership and tight AWS integration. Both support OIDC and a governance-first design.
- Roles later: learner, admin, instructor. Least privilege by default. Clear guest vs registered
  separation. No shared admin secrets in frontend (today's ADMIN_TOKEN is already server-side only).

Guest vs registered (future):
- Guest: no account, temporary score, 168-hour expiry by browser/guest token (today already done
  via query-time filtering; DynamoDB TTL later).
- Registered: profile, run history, score over time, favorites, weak areas, study paths.

Persistence comparison (plan only):
- Current: MongoDB (works now, single managed DB).
- SQLite: cost-conscious single-instance EC2 MVP; great when low traffic and one node. Needs a
  backup/restore plan (scheduled file backups + export/import). Not for multi-instance.
- PostgreSQL: when multi-user, multi-instance, higher concurrency is needed.
- DynamoDB: AWS-native serverless; TTL for guest scores; pairs with Cognito + Lambda.
- Migration path: keep data-access behind a thin layer so SQLite -> Postgres -> DynamoDB is a
  swap, not a rewrite. Define export/import scripts early.

Deployment comparison (plan only, do not migrate in v0.3):
- Current hosted (Emergent): simplest today; keep for v0.3.
- Low-cost EC2: React via Nginx, FastAPI behind Nginx reverse proxy, systemd or Docker Compose for
  the Python service (PM2 only if a Node service is added), SQLite for low concurrency, CloudFront
  for static assets, HTTPS via managed cert (ACM), AWS Budgets for cost alerts. Backup the SQLite
  file on a schedule. Honest note: EC2 is not the default pick; prefer it only when it is clearly
  the simplest and cheapest for a single low-traffic instance.
- Serverless (CloudFront + S3 for frontend, API Gateway + Lambda for FastAPI via an adapter,
  DynamoDB): best for spiky/low baseline traffic and pay-per-use; more moving parts to set up.
- Containerized (ECS Fargate or App Runner + RDS/Dynamo): clean scaling without node management.
- Full AWS-native: Cognito + API Gateway/Lambda + DynamoDB + CloudFront + WAF + CloudWatch, with
  Secrets Manager/Parameter Store for secrets and KMS for encryption.

Security/governance roadmap (plan only):
- Least privilege, explicit authn/authz boundaries, audit-friendly admin actions, retention rules
  for guest scores, privacy-aware progress storage, secure-by-default APIs, rate limiting and abuse
  prevention later, central logging/monitoring.
- AWS services to consider later: IAM, Secrets Manager / Parameter Store, KMS, CloudWatch, WAF,
  GuardDuty, Inspector, Audit Manager, and Amazon Verified Permissions for fine-grained app authz
  once roles and policies grow.

Cost-consciousness: start static-first and local-progress to keep v0.3 near zero added cost. Defer
any paid AWS footprint until registered mode and real traffic justify it.
